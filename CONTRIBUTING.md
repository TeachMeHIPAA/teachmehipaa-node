# Contributing

## Setup

Use the Node version in `.nvmrc` (any Node 20 or newer works), then:

```sh
npm ci
npm run lint        # ESLint and Prettier
npm run typecheck   # tsc --noEmit over src, test and scripts, then examples/
npm test            # unit tests and the doc tests of the README and guides
npm run build       # ESM and CJS bundles with declarations, into dist/
npm run check:dist  # loads dist/ as ESM and CJS; type-checks the doc samples against it
npm run docs        # the TypeDoc site, into site/
```

## Generated and hand-written code

The library is a hand-written core plus a resource and model layer generated
from the vendored IR (ADR-0001).

| Path                                         | Origin                                                            |
| -------------------------------------------- | ----------------------------------------------------------------- |
| `src/core/`, `src/client.ts`, `src/index.ts` | Hand-written                                                      |
| `src/extensions/`                            | Hand-written methods added to generated resources (see below)     |
| `src/models/`, `src/resources/`              | Generated by `npm run generate`; do not edit                      |
| `docs/reference/`                            | Generated by `npm run generate`; do not edit                      |
| `scripts/generate.ts`, `scripts/generator/`  | The generator                                                     |
| `openapi/`                                   | Vendored from the monorepo; do not edit (see `openapi/README.md`) |

Every generated file starts with a "Generated from openapi/sdk-ir.json — do not
edit" banner. To change generated code, change the generator, or fix the IR
upstream in the monorepo's `tooling/sdk-ir` and re-vendor it.

A resource that needs a hand-written method, such as `events.tail`, is listed
in `EXTENDED_RESOURCES` in `scripts/generator/resources.ts`. The generator then
names its class `<Name>Base` (`EventsBase`), and
`src/extensions/<file>.ts` extends it under the plain name (`Events`), which is
the class the client exposes. Add the new method to `HAND_WRITTEN_METHODS` in
`test/generated-surface.test.ts`.

Methods whose IR response kind is `operation` return the hand-written
`Operation` from `src/core/operations.ts` (`wait()`, `exportResult()`). The
spec leaves `Operation.response` untyped; to type it for an operation, add its
operationId and a type from that file to `OPERATION_RESPONSES` in
`scripts/generator/resources.ts`.

## Regenerating

1. Copy `openapi.developer.json`, `sdk-ir.json` and `sdk-ir.schema.json` from
   one IR build into `openapi/`, and its `source.release` into
   `OPENAPI_VERSION`.
2. Run `npm run generate` (it runs the TypeScript generator through `tsx`, a
   dev dependency, so any supported Node works). It validates the IR against
   its schema, then rewrites `src/models/`, `src/resources/` and
   `docs/reference/resources.md`, deleting files the IR no longer produces.
3. Run `npm test`. The generated-surface test fails if the committed output
   differs from what the generator writes, or if any spec operation lacks
   exactly one public method.
4. Run `npm run test:contract`, add the new operations to the contract suite
   if they belong to a resource family it doesn't cover yet, and add a
   CHANGELOG entry.

The generator reads these IR method fields into each request it emits:
`orgScoped` (prefix the path with the client's Organization), `security`
(`none` sends no Access token), `retrySafe`, `idempotencyKey`, `ifMatch`,
`ifNoneMatch`, the request body's content type and binary parts, and the
response kind.

## Tests

| Command                 | What it runs                                                                                              |
| ----------------------- | --------------------------------------------------------------------------------------------------------- |
| `npm test`              | Unit tests: the public client with a fake transport, webhook vectors, generated coverage, the README test |
| `npm run test:contract` | The client against a Prism mock of `openapi/openapi.developer.json`                                       |
| `npm run test:sandbox`  | Read-only smoke test against the real Sandbox; skipped without credentials                                |

Unit tests cross only the seams agreed in the spec: the public client with a
fake transport injected (`test/support/fake-transport.ts`) and a fake clock,
the pure webhook functions, and the generated surface. Take expected values
from the spec, the research docs or worked examples, never from the code
under test. No test calls the live API.

### Doc samples

`test/readme.test.ts` and `test/guides.test.ts` keep the README and every
guide in `docs/guides/` honest, through the harness in
`test/readme/harness.ts`. Every TypeScript block must carry an id in its info
string, as in ` ```ts sample=quickstart `, unique within its test file. The
tests type-check every sample with the repo's compiler settings, and run each
runnable sample against the fake transport, with `"@teachmehipaa/node"` pointing at
`test/readme/runtime.ts`, then check what it printed and sent. A sample that
can't run (it touches the disk or starts a server) is listed in
`TYPE_CHECKED_ONLY` with the reason. A sample that uses `client` without
creating it gets a Sandbox client bound to `org_acme` prepended; names that
stand for the reader's own code, such as `cursors`, are declared in the
harness's `PLACEHOLDERS`. To add a sample, give it an id and add a
`runs(...)` case or a `TYPE_CHECKED_ONLY` entry. A ` ```js sample=<id> `
block is CommonJS: `npm run check:dist` runs it against the build, with a
`fetch` that answers every request with a Course. Shell blocks are not
tested.

`docs/reference/code-samples.json` comes from the table in
`scripts/generator/samples.ts`: one program per IR operationId, using the
example values every TeachMeHIPAA SDK shares. The generator fails when an
operationId has no sample or a sample calls the wrong method, and
`test/code-samples.test.ts` type-checks each program against `src/` (and
against `dist/` under `check:dist`).

### Contract suite

`npm run test:contract` starts Prism (`@stoplight/prism-cli`, a dev
dependency) on a free port from `test/contract/prism.ts`, and runs
`test/contract/contract.test.ts`, one representative call per resource
family, against it. The client uses `staticTokenProvider` and an explicit
`organizationId`, since Prism can't mock the form-encoded token endpoint.
Prism answers a request that breaks the spec with a 4xx, which fails the
call, and the suite also fails on any request violation Prism reports in
`sl-violations`.

Prism serves static responses built from the spec's schemas. `--dynamic` and
`--errors` are off on purpose: Prism's own generated responses break the spec
(static strings ignore `pattern`; dynamic numbers break OpenAPI 3.1
`exclusiveMinimum`), so either flag makes valid SDK requests fail. Response
violations are therefore ignored; the suite still checks that each response
reads into the typed model.

### Sandbox smoke test

```sh
TMH_SANDBOX_CLIENT_ID=cli_… TMH_SANDBOX_CLIENT_SECRET=tmh_cs_… npm run test:sandbox
```

It introspects the token, lists Courses and lists Learners in the Sandbox
Environment. It never writes, and CI never runs it.

## Documentation

| Path                               | What it is                                                    | Kept in sync by                                                  |
| ---------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| `README.md`                        | Overview, install, quickstart, links                          | `test/readme.test.ts`                                            |
| `docs/guides/*.md`                 | Task guides                                                   | `test/guides.test.ts`                                            |
| `docs/reference/resources.md`      | Every resource and method, from the IR                        | `npm run generate`; the generated-surface test                   |
| `docs/reference/code-samples.json` | One program per operationId, for the monorepo's API reference | `npm run generate`; `test/code-samples.test.ts` type-checks each |
| `docs/README.md`                   | Index of all documentation                                    | Hand-written                                                     |
| `examples/*.ts`                    | Runnable programs against the Sandbox                         | `npm run typecheck` (`tsconfig.examples.json`)                   |
| TypeDoc site                       | The API reference, from the TSDoc in `src/`                   | `npm run docs` in the Docs workflow                              |

When you change the public interface, update the guide that covers it; the
doc tests fail if a sample no longer compiles or behaves as shown. Write for
partner developers, in the terms of `GLOSSARY.md`.

`npm run docs` builds the TypeDoc site into `site/` from `src/index.ts`, with
the README as its home page and the guides, the resource reference and the
examples index as pages. `typedoc.json` sets `treatWarningsAsErrors`, so an
unexported type in the public interface or a broken link fails the build.
`typedoc-plugin-missing-exports` documents the classes the client exposes but
doesn't export, such as the resource classes, and
`scripts/typedoc-document-titles.mjs` names each page after its first
heading. TSDoc on generated code comes from the IR's descriptions; fix those
upstream.

`.github/workflows/docs.yml` builds the site on every pull request and push,
and on `main` deploys it to GitHub Pages with `actions/deploy-pages`. Pages
must be enabled once in the repository settings (Settings → Pages → Source:
GitHub Actions) before the first deploy succeeds; until then the deploy job
fails, and the links to `https://teachmehipaa.github.io/teachmehipaa-node/` 404.

## Releasing

Releases go out from `.github/workflows/release.yml`, which runs only when
dispatched by hand. A run with `publish` unchecked (the default) runs lint,
type checks, unit and contract tests, the build, `check:dist` and
`npm pack --dry-run`, and publishes nothing. With `publish` checked it then
runs `npm publish` in the `npm` environment through npm trusted publishing
(OIDC, no npm token stored in the repo). `publishConfig` sets public access
and provenance.

npm trusted publishing for `@teachmehipaa/node` is configured on npmjs.com:
organization `TeachMeHIPAA`, repository `teachmehipaa-node`, workflow
`release.yml`, environment `npm`. (npm only offers this once a package
exists, so 1.0.0 was published by hand.) To ship a release:

1. In one PR: set `version` in `package.json` and `src/version.ts`, and move
   the CHANGELOG's Unreleased entries under that version with the date.
2. After it merges, dispatch **Release** on `main` once without `publish`
   and check the packed file list, then again with `publish` checked.
3. Tag the release commit `v<version>`.
